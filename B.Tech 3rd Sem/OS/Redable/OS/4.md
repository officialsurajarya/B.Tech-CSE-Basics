# 📘 Unit 4: Deadlocks

## 1. Unit Title
**Deadlocks: Conditions, Prevention, Avoidance, Detection, and Recovery**

## 2. Introduction
In a multiprogramming environment, multiple processes compete for a finite number of resources (like CPU cycles, memory, printers, etc.). A process requests a resource; if it is not available, the process goes into a waiting state. Sometimes, a waiting process can never change its state because the resource it needs is held by another waiting process. This infinite waiting situation is called a **Deadlock**. 

*Ek simple example samajhiye:* Jaise ek traffic jam jahan chaaro taraf se gaadiyan aa gayi hain, aur koi aage nahi badh pa raha kyunki sab ek doosre ka rasta block karke khade hain. Har koi wait kar raha hai ki doosra hate toh main jaaun, aur koi nahi hat pata. Operating System mein bhi exactly yahi hota hai.

## 3. All Topics

### Topic 4.1: Definition of Deadlock
👉 **Definition:** A set of processes is in a deadlocked state when **every process in the set is waiting for an event that can be caused only by another process in the set**.

👉 **Explanation:** If Process P1 holds Resource R1 and requests Resource R2, while Process P2 holds Resource R2 and requests Resource R1, both processes will wait indefinitely for each other to release the resources. Neither can proceed.

👉 **Examples:**
*   **Technical Example:** Two programs try to write to the same file. Program A locks the file and requests a printer. Program B locks the printer and requests the file. Both wait forever.
*   **Real-world Example:** A law passed in Kansas stated: “When two trains approach each other at a crossing, both shall come to a full stop and neither shall start up again until the other has gone.” This practically means neither train will ever move.

### Topic 4.2: Necessary and Sufficient Conditions for Deadlock
👉 **Definition:** For a deadlock to occur, four specific conditions must hold **simultaneously** in a system. These are known as the **Coffman Conditions**.

👉 **The Four Necessary Conditions:**
1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode. *Agar resource shareable hai (jaise Read-only file), toh deadlock nahi hoga. Par printer ek time pe ek hi use karega, so it's mutually exclusive*.
2.  **Hold and Wait:** A process must be holding at least one resource and waiting to acquire additional resources that are currently being held by other processes. *Jaise buffet mein aapke paas plate hai par spoon ke liye wait kar rahe ho, aur plate chhod nahi rahe*.
3.  **No Preemption:** Resources cannot be preempted. A resource can be released only voluntarily by the process holding it, after its task is finished. *OS zabardasti resource chheen nahi sakta*.
4.  **Circular Wait:** A set of waiting processes {$P_0, P_1, ..., P_n$} exists such that $P_0$ is waiting for $P_1$, $P_1$ is waiting for $P_2$, ..., and $P_n$ is waiting for $P_0$. This forms a circular chain of dependencies.

👉 **Sufficient Condition (Resource Allocation Graph - RAG):**
A Resource Allocation Graph (RAG) is a directed graph used to describe the deadlock visually. Processes are circles, and resources are rectangles. 
*   **If RAG has NO cycle:** The system is **NOT** deadlocked.
*   **If RAG has a cycle:**
    *   If each resource type has exactly **one instance**, a cycle implies Deadlock (Necessary and Sufficient).
    *   If resource types have **multiple instances**, a cycle does NOT necessarily mean deadlock (May or may not be deadlocked).

### Topic 4.3: Deadlock Prevention
👉 **Definition:** Designing the system protocols in such a way that **at least one** of the four necessary conditions for deadlock cannot hold. *Agar ek bhi pahiya (condition) tod diya, toh deadlock ki kursi gir jayegi.*.

👉 **Methods to Violate Conditions:**
1.  **Preventing Mutual Exclusion:** Make resources shareable. 
    *   *Disadvantage:* Not practical for inherently non-sharable resources like mutex locks or printers.
2.  **Preventing Hold and Wait:** Require a process to request all its resources before it begins execution, OR it can request resources only when it holds none.
    *   *Disadvantage:* Very low resource utilization and high chances of starvation.
3.  **Preventing No Preemption:** If a process holding resources requests another resource that it cannot get immediately, it must release (preempt) all its currently held resources.
    *   *Disadvantage:* Only works for resources whose states can be easily saved/restored (like CPU registers), not for printers or tape drives.
4.  **Preventing Circular Wait:** Impose a strict total ordering of all resource types. A process must request resources in an increasing order of enumeration.
    *   *Advantage:* This is the most practical and widely used approach to prevent deadlock.

### Topic 4.4: Deadlock Avoidance and Banker’s Algorithm
👉 **Definition:** Deadlock avoidance requires the OS to be given *advance information* about the maximum resources a process will need. The OS then checks dynamically to ensure the system never enters an "unsafe state".

👉 **Safe State vs. Unsafe State:**
*   **Safe State:** The system can allocate resources to all processes in some order (Safe Sequence) without causing a deadlock.
*   **Unsafe State:** A state where a safe sequence does not exist. An unsafe state *may* lead to a deadlock.

👉 **Banker’s Algorithm (For Multiple Instances):**
Named because it’s used in banking systems to ensure the bank never runs out of cash to satisfy customer needs.

👉 **Data Structures Used:** Let $n$ = processes, $m$ = resource types.
*   **Available:** Array of size $m$ indicating available resources of each type.
*   **Max:** $n \times m$ matrix defining maximum demand of each process.
*   **Allocation:** $n \times m$ matrix defining resources currently allocated to each process.
*   **Need:** $n \times m$ matrix indicating remaining resource needs. **Formula: Need[i][j] = Max[i][j] - Allocation[i][j]**.

👉 **Safety Algorithm Steps:**
1.  Initialize `Work = Available` and `Finish[i] = false` for all processes.
2.  Find a process $P_i$ such that:
    *   `Finish[i] == false`
    *   `Need_i <= Work`
    *(If no such process exists, jump to Step 4)*
3.  If found, assume the process completes and releases resources:
    *   `Work = Work + Allocation_i`
    *   `Finish[i] = true`
    *   Jump back to Step 2.
4.  If `Finish[i] == true` for all $i$, the system is in a **Safe State**.

👉 **Resource-Request Algorithm:** When a process $P_i$ requests resources:
1.  Check if `Request_i <= Need_i`. If yes, proceed. Else, error.
2.  Check if `Request_i <= Available`. If yes, proceed. Else, process must wait.
3.  *Pretend* to allocate resources:
    *   `Available = Available - Request_i`
    *   `Allocation_i = Allocation_i + Request_i`
    *   `Need_i = Need_i - Request_i`
4.  Run Safety Algorithm. If safe, grant the request. If unsafe, rollback and process waits.

### Topic 4.5: Deadlock Detection
👉 **Definition:** If a system does not use prevention or avoidance, it must employ an algorithm to detect if a deadlock has occurred by examining the system state.

👉 **Key Concepts & Subtopics:**
1.  **Single Instance of Each Resource Type:**
    *   Uses a **Wait-For Graph**. It is created by removing the resource nodes from the Resource Allocation Graph and joining the process nodes directly.
    *   An edge $P_i \rightarrow P_j$ implies $P_i$ is waiting for $P_j$ to release a resource.
    *   **Rule:** If the wait-for graph contains a cycle, a deadlock exists.
2.  **Multiple Instances of a Resource Type:**
    *   Uses an algorithm similar to Banker's Algorithm.
    *   It maintains `Available`, `Allocation`, and `Request` matrices.
    *   It optimistically assumes that processes with `Request <= Available` will finish and return their allocated resources. If some processes are left unable to finish, they are deadlocked.

### Topic 4.6: Recovery from Deadlock
👉 **Definition:** Once a deadlock is detected, the system must take action to break it. This is called deadlock recovery.

👉 **Subtopics (Methods of Recovery):**
1.  **Process/Thread Termination:**
    *   *Abort all deadlocked processes:* Very harsh, breaks deadlock but discards a lot of partial computations.
    *   *Abort one process at a time:* Kill one process, run detection algorithm. If deadlock exists, kill another. Priority, execution time, and remaining resources are factors used to choose the victim.
2.  **Resource Preemption:**
    Take resources away from some processes and give them to others until the cycle breaks. 
    *   *Selecting a Victim:* Choose the process that costs the minimum to preempt.
    *   *Rollback:* The preempted process cannot continue normally; it must be rolled back to a safe state or completely restarted.
    *   *Starvation:* Ensure that the same process is not always picked as the victim, otherwise it will starve.

👉 **Deadlock Ignorance (The Ostrich Algorithm):**
*   **Concept:** Pretend deadlocks never occur. *Jaise ostrich tufaan aane pe ret mein sar daal leta hai.*
*   **Why use it?** Deadlock prevention/avoidance is extremely costly in terms of performance. Since deadlocks are rare in standard PCs, OS like Windows and Linux simply ignore them. If a deadlock happens, the user has to manually reboot the system or force-kill the app.

📊 **Comparison: Deadlock Prevention vs. Deadlock Avoidance**

| Feature | Deadlock Prevention | Deadlock Avoidance |
| :--- | :--- | :--- |
| **Basic Approach** | Breaks at least one of the 4 necessary conditions. | Checks dynamically before allocating to avoid unsafe states. |
| **Strictness** | Highly strict (Conservative approach). | Less strict, checks on the fly (Runtime). |
| **Resource Utilization** | Low utilization (due to strict rules). | Better resource utilization. |
| **Algorithm** | Ordering resources, no hold & wait. | Banker's Algorithm. |
